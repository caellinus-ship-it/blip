# Blip Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A native Mac menu-bar app where a shortcut summons an arcade-style pixel creature in a spaceship that answers questions about the screen through a hidden Claude Code session.

**Architecture:** A SwiftPM package with two halves. `BlipCore` is pure Swift with no UI: sprites, motion, trails, scene rendering into a low-resolution pixel framebuffer, settings, and all the text protocol with the hidden `claude` process. `Blip` is the AppKit/SwiftUI shell: a click-through overlay window that shows the framebuffer scaled up with nearest-neighbour filtering, a chat panel, screen capture, dictation, sounds and settings. Everything testable lives in `BlipCore`; the shell stays thin.

**Tech Stack:** Swift 6.3 (language mode 5), SwiftPM, Swift Testing, AppKit, SwiftUI, Core Animation, ScreenCaptureKit, Speech, AVFoundation, Carbon hot keys, ServiceManagement. No third-party dependencies.

**Spec:** `docs/superpowers/specs/2026-11-17-blip-design.md`. Look reference: `docs/reference/mockup.html`.

## Global Constraints

- macOS 26.2 only; Xcode 26.6; Swift 6.3. `Package.swift` uses `// swift-tools-version: 6.0`, `platforms: [.macOS("26.0")]`, `swiftLanguageModes: [.v5]`.
- No third-party packages.
- Not sandboxed. Menu-bar app (`LSUIElement` true). Bundle id `com.blip.assistant`. Installed to `~/Applications/Blip.app`, signed with the one codesigning identity already on this Mac.
- All art is original and comes from `docs/reference/mockup.html`. Never copy sprites from a real game.
- Animation logic runs on a fixed 60 Hz tick. All positions are whole arcade pixels. Colors step through ramps; nothing fades by alpha.
- One arcade pixel is 2, 3 or 4 screen points (size small, medium, large).
- The hidden session runs with exactly these flags: `-p --model <haiku|sonnet> --safe-mode --strict-mcp-config --tools "" --no-session-persistence --system-prompt <text> --input-format stream-json --output-format stream-json --verbose --include-partial-messages`.
- Screenshots are taken only when a question is sent, stay in memory, and are never written to disk.
- The assistant never acts on the computer. Replies are plain text.
- Commits go to a local git repository in `blip/`. Nothing is pushed.
- Every commit message ends with the `Co-Authored-By:` trailer for the model that wrote it (the one your harness specifies).
- Run all commands from the repository root.

## Review Focus

1. **Shortcut mashing.** Pressing the shortcut during fly-in, during fly-off, or many times fast must never leave two characters, a stuck overlay, or an orphaned `claude` process. (Tests: Task 3 `dismissDuringFlyIn`, Task 6 `summonStateMachine`.)
2. **Broken stream.** Output lines split across reads, non-JSON lines, or the hidden process dying mid-answer must produce an error bubble and a fresh standby process, never a hang or crash. (Tests: Task 7 `lineBufferSplits`, `parserIgnoresGarbage`; Task 8 `--brain-check` kill test.)
3. **Marker lookalikes.** Replies such as "Looking at your screen…", "LOOK: here", `LOOK:99` with only three windows, or a second `LOOK` in one question must be shown as text or answered gracefully. (Tests: Task 7 `gate*`.)
4. **Empty and double sends.** Enter on an empty box, or Enter while an answer is still streaming, must do nothing. (Tests: Task 10 `chatLogRejects*`.)
5. **Odd screens and window lists.** Drawing off the edge of the buffer, windows with empty titles, and more than 20 windows must clip, fall back to the app name, and truncate. (Tests: Task 1 `fillClips`, Task 7 `windowList*`.)

### Task 3: Ship motion

**Files:**
- Create: `Sources/BlipCore/ShipMotion.swift`
- Test: `Tests/BlipCoreTests/ShipMotionTests.swift`

**Interfaces:**
- Produces:
  - `public enum HoverMotion: String, Codable, CaseIterable { case figure8, bob, still }`
  - `public enum Phase: Equatable { case flyIn, hover, flyOut, gone }`
  - `public struct ShipMotion { public init(bufferWidth: Int, bufferHeight: Int, hover: HoverMotion); public private(set) var phase: Phase; public private(set) var x: Int; public private(set) var y: Int; public private(set) var anchorX: Int; public private(set) var anchorY: Int; public var flying: Bool { get }; public mutating func tick(); public mutating func dismiss(); public mutating func drag(dx: Int, dy: Int) }`
  - `(x, y)` is the top-centre of the ship sprite. `(anchorX, anchorY)` is the hover centre, initially the buffer centre.
  - Values: fly-in is 90 ticks, `y` from `bufferHeight + 30` to `anchorY` along `1 - (1 - p)³`. Hover uses `h = 1.3 * hoverTicks / 60`: figure 8 is `x = anchorX + round(6 sin h)`, `y = anchorY + round(3 sin 2h)`; bob is `y = anchorY + round(3 sin h)`; still does not move. Fly-off is 48 ticks from the position at dismissal to `y = -45` along `p³`, then `gone`. `flying` is true in `flyIn` and `flyOut`. `drag` moves the anchor (and the ship) and is ignored outside `hover`. `dismiss` works from `flyIn` or `hover` and is ignored otherwise.

### Task 4: Trails

**Files:**
- Create: `Sources/BlipCore/Trails.swift`
- Test: `Tests/BlipCoreTests/TrailsTests.swift`

**Interfaces:**
- Consumes: `PixelBuffer`, `Sprite`, `Art.confetti`, `ColorRamp`.
- Produces:
  - `public enum TrailStyle: String, Codable, CaseIterable { case comet, flame, rings, echoes, lightning, confetti }`
  - `public struct SeededRandom { public init(seed: UInt64); public mutating func next() -> Double }` (SplitMix64, result in 0..<1)
  - `public struct TrailSystem { public init(style: TrailStyle, seed: UInt64); public private(set) var power: Double; public var boltLengths: [Int] { get }; public mutating func tick(shipX: Int, shipY: Int, exhaustY: Int, flying: Bool); public func draw(into b: inout PixelBuffer, ramp: ColorRamp, silhouette: [(Sprite, dx: Int, dy: Int)]) }`
  - `power` starts at 1 and each tick moves toward its target (1 flying, 0 hovering) by `(target - power) * 0.035`. Every length and rate below is computed from `power`, so nothing changes abruptly when the ship stops.
  - `silhouette` is the creature and ship sprites with their offsets from `(shipX, shipY)`; only `echoes` uses it.

Port each style from `trail()` in `docs/reference/mockup.html`, working in arcade pixels (divide the mockup's point values by 3) and replacing its two-value `fly ? a : b` constants with these interpolations (`p` is `power`):

| Style | Values |
|---|---|
| comet | one point per tick at the exhaust; life `28 + 18p` ticks; falls `0.5 + 0.5p` px per tick; widths 9, 7, 5, 3, 1 by age fifth; white 3 px core while age < 30%; skip odd ages after 65% |
| flame | redrawn every 3 ticks; length `6 + 12p` plus 0 to 3 flicker; row width `max(1, round((1 - f) * 7))` plus 0 or 1; white core where `f < 0.45` and width > 3; 5 sparks |
| rings | a ring every `round(26 - 18p)` ticks; life 44; falls `0.4 + 0.33p` px per tick; radius `2.7 + 0.3 * age`, vertical radius 40% of that; skip every other pixel after half life |
| echoes | a copy every 4 ticks; life 24; while hovering copies drift down `0.53 * (1 - p)` px per tick; checker dither after 30% life; color `ramp.step(0.25 + 0.75f)` |
| lightning | three bolts with directions -1, 0, +1 starting at offsets -4, 0, +4; bolt `b` regenerates when `(tick + b) % 3 == 0`; middle length `round(15 + 21p)`, sides 72% of that; each row steps `round((r - 0.5) * 2.6 + dir * 0.45)`; middle width 3 then 2 after 60%, sides 2 then 1 after 50%; white 1 px core for the first 55% (middle) or 30% (sides); a 2 px fork every sixth row before 80%; skip odd rows after 82%; a 10 px white flash at the exhaust on ticks where `tick % 4 < 2` |
| confetti | a piece every `round(9 - 7p)` ticks; life `36 + 24p`; falls `1/3 + (1/6 to 5/6) * (0.5 + 0.5p)`; sways with `sin((age + k * 9) / 6) * 0.27`; blinks on odd ticks after 70% life; color is white, light or main by piece |
